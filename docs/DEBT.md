# DEBT.md — S9 audit (docs/refactor/SYSTEMS.MD)

Generated by a multi-agent audit pass (parallel scan → adversarial verify) against
`scripts/` for four CLAUDE.md rules: missing type hints, hardcoded values that should be
`@export`, direct `$Node`/cross-component reaches instead of the SignalBus/accessor
convention, and leftover Godot 3 idioms. 54 findings total. Mechanical, verified-safe
fixes were applied; everything else is cataloged here instead of guessed at, per
CLAUDE.md's own instruction for ambiguous judgment calls.

## Important gotcha found while applying this audit

**This project's Godot/GDScript setup treats "variable type inferred as Variant" as a
compile ERROR, not a warning.** The audit tool (and my own first pass extrapolating its
"mechanical" patterns to sibling lines) treated `var x = expr` → `var x := expr` as a
uniformly safe, mechanical rewrite whenever `expr`'s *runtime* type was knowable/expected.
That is not the same question as whether `expr`'s *static* type is Variant — and when it
is, `:=` fails to compile here with `Parse Error: Cannot infer the type of "x" variable
because the value doesn't have a set type` (or, for one case, `The variable type is being
inferred from a Variant value ... (Warning treated as error.)`), and the whole script (and
anything that transitively loads it, including autoloads) fails to load.

Three concrete shapes this took, all of which look "obviously fine" by runtime reasoning
but are Variant at the *static* level:

1. **Untyped Dictionary/Array indexing.** `build_spots: Dictionary`, `_slot_units: Array`,
   `owned_allies: Array`, `_pinned: Array`, `lights: Array`, `_towers: Array` are all
   declared without an element type. Indexing them (`build_spots[cell]`, `_slot_units[i]`,
   `.current_habit` chained off either) is Variant even though the *contents* are always a
   specific class — the compiler doesn't know that.
2. **`GDScript.new()`.** A script preloaded as `const X = preload("res://....gd")` is typed
   `GDScript`; calling `.new()` on it returns Variant because the engine can't statically
   know what class results from a dynamically-loaded script.
3. **`load(path).instantiate()` with no explicit target type.** `load()` alone returns a
   concrete `Resource`, and `ResourceLoader.load(...)` alone is likewise safe to infer —
   but chaining `.instantiate()` off a bare `Resource`-typed value is Variant, because
   `instantiate()` isn't declared on `Resource` itself (only on `PackedScene` and similar).
   `var x: Game = load(path).instantiate()` is safe (explicit annotation bypasses
   inference entirely); `var x := load(path).instantiate()` is not.

Several of the audit's own "adversarially verified safe" findings hit case 1
(`mirror.gd`, `defender_unit.gd`, `projectile.gd`, `enemy.gd`, `build_spot.gd`,
`barracks.gd`) and were caught by `verify.sh` immediately (compile failure cascaded into
~11 unrelated test failures on the first attempt, since these are non-autoload scripts
whose `class_name` registration is part of the global class-list build that every
Game-instantiating test depends on). When I then bulk-applied the same "mechanical"
`:=` pattern to sibling lines across ~25 dev/test-harness files myself (not something the
audit had verified), several more instances of all three shapes surfaced, mostly as a
**hang** rather than a clean failure: a script parse error means the scene never
finishes `_ready()`, so the process sits until `verify.sh`'s 120s per-test timeout kills
it, which looks like a stuck test rather than a compile error until you read the actual
`.dev/<test>.log`.

Files where a `:=` conversion (either the audit's or my own extrapolated one) had to be
reverted back to `=` for this reason: `mirror.gd`, `enemy.gd`, `build_spot.gd`,
`barracks.gd`, `defender_unit.gd`, `projectile.gd`, `_shot_flat.gd`, `_shot_shadows.gd`,
`_shot_fog.gd`, `_shot_aim.gd`, `_perf_shadows.gd`, `_test_effort.gd`,
`_test_fog_bandwidth.gd`, `_test_levels.gd`, `_shot_verify.gd`, `_test_mapeditor.gd`,
`_test_game_iso_slice.gd`, `_test_nutrition_guild.gd`, `_test_phase4.gd`,
`_test_phase7.gd`, `_test_sink.gd`. Every one of these was caught by actually running
`verify.sh` after applying the batch (several as a 120s per-test hang rather than a clean
error, since a script parse failure means the scene's `_ready()` never completes) — not by
static reasoning alone, which is exactly the point of the takeaway below.

A fourth shape, easy to miss: **a concretely-typed method's return type only helps if the
*receiver* is itself concretely typed.** `spawn_distraction()` is declared `-> Distraction`
on `Game`, so `var d := some_game.spawn_distraction(...)` is safe wherever `some_game` is
typed `Game` — but `_test_phase4.gd` happened to declare its local as `var game: Node =
load(...).instantiate()` (generic `Node`, not `Game`), and `Node` has no
`spawn_distraction`/`projectile_pool` members, so the same call on `game` there is Variant
regardless of what `Game` itself declares. Caught the same way (a 120s timeout, not a clean
failure) after being wrongly assumed safe from the callee's signature alone.

**Takeaway for any future mechanical `:=` bulk pass:** don't trust "the RHS obviously
resolves to class X at runtime" reasoning alone. Check the actual *declared* type of the
receiver AND every intermediate step (container element types, chained-call return types),
and when in doubt, apply and run `verify.sh` — the compiler is the ground truth here, not
static-analysis inference by an agent (or by me).

## Judgment calls — hardcoded values vs. `@export` (13, not applied)

Per CLAUDE.md, content/balance numbers belong in `data/` as exported fields, not script
constants. All 13 below are real hardcoded balance numbers with no `@export` override, but
whether each is a genuine oversight or a deliberately-uniform game-wide rule is a design
call, not a mechanical fix — cataloged for a future balance pass, not applied:

1. `components/arc_profile.gd:29,34,38,68-70` — `DMG_EXP`/`RATE_EXP`/`HIT_EXP`/knockback
   &stagger constants shaping every habit's cone-damage curve. Lower confidence: the class
   doc frames this as one deliberately-shared curve, not per-habit content.
2. `tower.gd:209` — Craving's "up to 25% faster fire rate" hardcoded `0.75` lerp factor.
3. `tower.gd:600` — `ART_FACING` dict of per-habit-id rotation corrections; grows by hand
   as more habits need the same PixelLab-angle fix.

5. `enemy.gd:504-505` — `KNOCK_BUDGET`/`KNOCK_REGEN`, global knockback-resist budget for
   every distraction. Lower confidence: framed as one shared anti-stunlock rule.
6. `game.gd:4190-4193` — Quick Hit's `QUICK_HIT_BASE`/`COOLDOWN`/`SPIKE`/`FLOOR_GAIN` —
   already reworked once per the surrounding comment, likely to be iterated on again.

8. `game.gd:4176` — `_TOLERANCE_DECAY_PER_SEC` base rate (already multiplied by a

9. `game.gd:4171-4172` — `CORE_ROUTINE_RADIUS`/`ANCHOR_ROUTINE_RADIUS` — already extracted

## Judgment calls — signal-bus / cross-component coupling (3, not applied)

Headline result: the codebase does **not** use raw `$Node`/`get_node()` paths for
cross-component coupling anywhere. All 3 findings are subtler — code that reaches past the
established accessor-method convention into another system's raw internals:

1. **Worth fixing** — `enemy.gd:370-385`, `Distraction._tick_disrupt()` reaches three
   levels into the tower system (`game.build_spots.values()` → `spot.current_habit` →
   reads `h.def.is_support()`/`h.in_routine`/`h.is_resting()`/`h.disrupted_left` directly,
   then calls `best.disrupt(...)`) — the one place in this file breaking its own
   otherwise-consistent "go through a Game accessor" convention.
2. **Worth a second look, likely intentional** — `defender_unit.gd:402-406`,
   `DefenderUnit._die()` reaches directly into `game.impact_fx_pool` (an `ObjectPool`
   implementation detail) instead of a `game.spawn_impact_fx(...)` wrapper — but this exact
   `acquire()`/position/`play()` sequence is inlined identically in `projectile.gd` and in
   `game.gd`'s own code, so it's a consistent, codebase-wide idiom rather than an isolated
   shortcut.
3. **Near the line, probably fine** — `barracks.gd:132`, `Barracks._spawn_slot()` calls
   `game.entities.add_child(u)` directly rather than through a `game.spawn_entity(...)`
   request — but this is exactly how `build_spot.gd` adds new Habits and how `game.gd`
   itself adds every other spawned object to the same `entities` container.
