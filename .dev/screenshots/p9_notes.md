# P9 — brain fog visual variants

Four screenshots of the SAME game moment (one `focus_timer` habit built and aimed, same
frame, same lit circle), differing only in how the UNLIT area is rendered. Generated by
`scripts/_shot_p9_fog_variants.gd` / `scenes/_shot_p9_fog_variants.tscn`.

- **`p9_fog_baseline.png`** — the shipped look, unchanged. `shaders/brain_fog.gdshader`,
  untouched. Flat purple-black (`fog_color`) at `fog_alpha` 0.88 wherever `light_mask` reads
  dark. This is the comparison anchor, not a new variant.

- **`p9_fog_blur.png`** — the unlit area shows a blurred view of the world instead of flat
  colour. Terrain blocks read as soft rounded smudges; you can tell *something* is there
  (a wall, a build spot) but not its edges.

- **`p9_fog_desaturate.png`** — the unlit area shows a full-resolution but desaturated
  (drained toward luminance) view of the world. Edges stay sharp — you can tell exactly
  what's there — but it reads as memory/grayscale rather than "currently seen".

- **`p9_fog_blur_desaturate.png`** — both at once: blurred AND desaturated.

All four use `shaders/brain_fog_preview.gdshader`, a **standalone candidate shader** — it is
not loaded anywhere in `game.gd` and does not change the shipped game. The harness swaps it
onto the game's existing `_fog_rect` node for one screenshot each, then the process exits;
nothing persists into a real play session.

## Technique: why not two full-scene `SubViewport`s

P9's text names "two `SubViewport`s sharing the same `World2D`, composited via a
`ViewportTexture`" as the default technique. That's already half-built: `_light_viewport`
(`game.gd` `_build_fog_layer()`) is exactly that pattern — a second render, composited via its
`ViewportTexture` into the fog shader's `light_mask` uniform. It's kept deliberately tiny
(240×135, additive light shapes only, no terrain/units/decor) specifically because a *full*
duplicate scene render — everything the main viewport draws, at up to ~300 concurrent
`Distraction` nodes — would double the frame's draw calls for what is, in the end, a
screen-space colour filter.

For "show a blurred/desaturated copy of the already-rendered frame," Godot 4 canvas_item
shaders have a cheaper native tool: `hint_screen_texture` (`SCREEN_TEXTURE` grabbed via a
backbuffer copy). This project already uses exactly that technique for a different mechanic —
`shaders/flatten.gdshader` (the Tolerance wash) drains saturation and collapses contrast by
sampling `hint_screen_texture`, with the same renderer (Forward Mobile / D3D12) already proven
to support it. `brain_fog_preview.gdshader` reuses that same approach: one `screen_tex`
uniform, a 9-tap box blur when `blur_px > 0`, and the identical luminance-drain desaturate
`flatten.gdshader` already does. No second full-scene render, no extra draw calls for the
world itself — one backbuffer copy plus a handful of texture taps in the existing fog pass.

This was a deliberate choice, not a shortcut taken to avoid the harder path: a genuine second
full-scene `SubViewport` would be the right tool if the two renders needed to diverge in
*content* (different camera, different visible objects) — they don't here, only in *post-
processing* of identical content, which is exactly what `SCREEN_TEXTURE` is for.

## Stretch-aspect risk — checked, not just assumed

`brain_fog.gdshader`'s header names a hard dependency: `window/stretch/aspect="keep"` (it
warns `SCREEN_UV`-based alignment would desync from the world under `"expand"` on non-16:9
windows). The concurrent session's uncommitted `project.godot` currently has that line
removed.

Checked empirically, not assumed: ran the screenshot harness twice — once at the project's
declared window size (1920×1080, 16:9, matches the 480×270 viewport exactly) and once with
`--resolution 1000x1400` (a badly mismatched, near-portrait aspect) — and compared the
captured `get_viewport().get_texture()` output. **Both runs produced a byte-for-byte
identical 480×270 image**: the internal game viewport did not resize, letterbox, or reveal
more/less world under the mismatched window. That is the fixed-content behavior `aspect=keep`
guarantees; `aspect=expand` would have changed the rendered content's extent and broken this
match. Godot 4's own engine default for `window/stretch/aspect` is `"keep"` — the same value
the removed line spelled out explicitly — so the removal reads as a redundant-default cleanup
(the kind the editor does automatically on save), not a behavior change. No desync found in
either run; the mask stayed glued to the world in both.

## Scope note

No `explored` grid, no new persisted visibility state, nothing wired into `is_pos_visible()`
or any gameplay path. `game._lit_cells` is untouched. These are visual-only candidates for a
"how should the unlit tier eventually read" comparison — the actual "explored but not
currently visible" *rule* is P10's decision, gated on the user playing P9 first.
